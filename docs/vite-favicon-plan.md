# Vite plugin favicon design and implementation plan

Ship a new major of `vite-plugin-favicon` that turns one source image into browser and touch icons in both `vite dev` and `vite build`. Favigen renders and caches the images. The Vite plugin publishes them, computes URLs for the places that reference them, and injects browser icon links. Developers can opt in to app icons and let their PWA plugin, backend, or a basic built-in helper handle the manifest.

## Where the project left off

The local checkout began with no commits or remotes. The source baseline is GitHub’s `latest` at `91fcc1d` (March 2023). Its changes since npm’s `1.0.8` are README corrections. The shipped code uses `favicons@6`, calls asset emission from a hook that also runs in dev, inserts reference IDs in place of URLs, and accumulates tag state across builds. The old test is a placeholder. The rework tracker covers dev, rebinding URLs and output overrides. The backend HTML proposal was closed unmerged. Install deprecations have their own issue. [Source](https://github.com/josh-hemphill/vite-plugin-favicon/tree/91fcc1d29e993fa904781cbc7be998bd483bce2f) · [npm 1.0.8](https://www.npmjs.com/package/vite-plugin-favicon/v/1.0.8) · [Rework #7](https://github.com/josh-hemphill/vite-plugin-favicon/issues/7) · [Dev #1](https://github.com/josh-hemphill/vite-plugin-favicon/issues/1) · [HTML fragment #3](https://github.com/josh-hemphill/vite-plugin-favicon/issues/3) · [Closed PR #2](https://github.com/josh-hemphill/vite-plugin-favicon/pull/2) · [Paths #6](https://github.com/josh-hemphill/vite-plugin-favicon/issues/6) · [Dependencies #26](https://github.com/josh-hemphill/vite-plugin-favicon/issues/26)

The owner’s Favigen `1.2.0` is the GitHub release at `0b1bbe8`. The tarball passed its published SHA-256 check and declares ESM, CommonJS and types, Node `>=22.12.0`, and Sharp `0.35.5`. The unscoped npm registry package “favigen” has the same version number and a different repository. Use the exact owner release URL as the plugin’s runtime dependency until a maintainer-controlled registry package is available. A clean npm consumer of a stand-in plugin tarball resolved Favigen transitively to the correct URL with recorded integrity and loaded both module formats. Its install still emitted deprecation warnings through Favigen’s legacy Jimp and ICO dependency chains. [Owner release](https://github.com/josh-hemphill/favigen/releases/tag/v1.2.0) · [Registry package metadata](https://registry.npmjs.org/favigen/latest) · [npm tarball dependencies](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#urls-as-dependencies)

A scratch fixture rendered a real PWA set through the release and exercised late emission with two HTML entries on Vite 7.3.8 and 8.3.8. In both, a later post-ordered hook could read the emitted files and resolve manifest icon URLs. Rollup exposed a newly emitted asset in the emitting hook’s bundle, while Rolldown exposed it in the next hook and provided a different bundle object there. This informs the companion contract and the order of collision checks. A second probe found that copied public files do not appear in the output bundle on either major. A same-name emission overwrote the public file on disk. For a later duplicate emission, Rollup warned and kept the first asset, while Rolldown exposed the replacement bytes to the next hook. A third probe confirmed producer → companion → validator on both majors with `write: false`. The full lifecycle and published plugin remain implementation work. [Favigen adapter design](https://github.com/josh-hemphill/favigen/blob/v1.2.0/docs/favigen-design.md#vite-and-manifest-ownership) · [Vite plugin hooks](https://vite.dev/guide/api-plugin)

## Developer experience

Target Vite `^7.3.0 || ^8.3.0` with a Node engine floor of `>=22.12.0`. Node 22 and 24 are the supported release matrix, with Node 26 exercised as a compatibility check. Ship ESM default and named `ViteFaviconsPlugin` exports and a callable CommonJS entry with the same named export and types. The npm install below is the stable 2.x install after release. [Vite 7 runtime](https://vite.dev/blog/announcing-vite7) · [Vite 8 runtime](https://vite.dev/blog/announcing-vite8.html)

```sh
npm install -D vite-plugin-favicon@^2
```

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import { ViteFaviconsPlugin as favicons } from 'vite-plugin-favicon'

export default defineConfig({
  plugins: [favicons({ source: './src/brand.svg' })],
})
```

In a Vite starter, remove its existing `<link rel="icon" href="/vite.svg">` from `index.html` to display the generated favicon. Dev then shows it on the first page load, and production links it from the built HTML. Leave an authored icon link in place to keep that page’s current icon.

Relative source paths are resolved against Vite’s configured `root`. Local absolute paths work, including checked-in artwork shared from another workspace folder. `favicons()` discovers one of `assets/logo.svg` or `assets/logo.png`. If both exist, the diagnostic lists both and asks for `source`. If neither exists, it lists the searched paths. One source can be self-contained SVG or static PNG, JPEG, or WebP. Recommend a square SVG with outlined text or a square PNG of at least 512 × 512 for the PWA profile. For an unsupported SVG feature, export to PNG. Share Favigen’s upscaling and small-icon aspect-ratio warnings, naming the affected target IDs. [Favigen sources and rendering](https://github.com/josh-hemphill/favigen/tree/v1.2.0#generate-icons-from-one-source)

| Profile | Logical outputs | References |
| --- | --- | --- |
| `web` (default) | `favicon.ico` with 16, 32 and 48 px frames, `favicon-32.png`, `favicon-48.png`, and a 180 px `apple-touch-icon.png` | Browser and Apple touch `link` elements with sizes and MIME types |
| `pwa` | All web assets plus 192 and 512 px PNGs for each of `any` and `maskable` | Same browser and touch links. App icons go to the manifest owner with MIME type, dimensions and purpose. |

The `web` target IDs are `favicon.ico`, `favicon.32`, `favicon.48` and `touch.180`. The `pwa` additions are `app.any.192`, `app.any.512`, `app.maskable.192` and `app.maskable.512`. For just a 32 px tab icon and the touch icon, use `ids: ['favicon.32', 'touch.180']`.

By default, all build assets live under `<build.assetsDir>/favicons/` and include a digest of their bytes before the extension, including the ICO. For example, `dist/assets/favicons/favicon-32.<digest>.png` is linked from `dist/index.html`. With `base: '/shop/'`, the dev middleware serves `/shop/assets/favicons/favicon-32.<digest>.png`, and preview serves the built tree at that same path. Configure `outputDir: 'brand/icons'` to put the icons under `dist/brand/icons/` and serve them under `/shop/brand/icons/` in dev. Target `name` changes the basename before the digest in both modes. `rootIco: true` emits the selected ICO as stable `favicon.ico` at the build root and serves it at `/shop/favicon.ico` in this example. If `ids` omits `favicon.ico`, remove `rootIco` or add that ID. Static hosting must expose the build root at the appropriate base. Keep this opt-in so a pre-existing `public/favicon.ico` remains usable for implicit browser requests.

| Option | Behavior |
| --- | --- |
| `profile`, `ids` | Choose a profile and optionally allowlist its stable target IDs. Unknown and empty selections produce a diagnostic. |
| `render`, `variants`, `targets` | Forward Favigen’s render controls and overrides by role or target. Paths in per-role/target `source` use the same root and watcher. Cropping, fit, padding, background and resampling can change pixels. The default preserves artwork without cropping, using transparency where supported and opaque backgrounds for touch and maskable roles. |
| `outputDir`, `rootIco`, target `name` | Change publication paths and names. The build’s general chunk/asset naming pattern leaves these explicit paths alone. `rootIco` and an ICO target name override are mutually exclusive. |
| `inject` | Defaults to true. False leaves HTML to the application and still publishes configured files and metadata. |
| `manifest` | Defaults to false. `{ mode: 'basic', name: 'My app' }` opts in and defaults the profile to `pwa`. An explicit profile or allowlist must include the regular 192 and 512 app icons. |
| `cache` | Uses Favigen’s disk cache below Vite’s `cacheDir`. Accepts `false` or an explicit absolute/local-root-relative cache directory. |

```ts
favicons({
  source: './src/brand.svg',
  manifest: { mode: 'basic', name: 'Shop' },
  variants: { favicon: { source: './src/small-mark.png', trim: true } },
  outputDir: 'brand/icons',
})
```

If a page already has an authored `rel="icon"` or `rel="shortcut icon"`, keep it and omit generated favicon links for that page. Apply the same rule independently to authored Apple touch links. Emit the icon assets either way. Warn once per file and role and show how to remove the specific Vite starter link to adopt generated icons. This preserves intentional light/dark icons and avoids precedence surprises. An existing public ICO is compatible with the default namespaced paths. If the developer requests `rootIco: true` and that file already exists, report its location and ask them to keep the public file or remove it before enabling root output. An existing manifest link is compatible with the default manifest-off configuration.

## Vite lifecycle and URLs

**Prepare.** Resolve configuration once without mutating the caller’s options. Track the primary source, variant files and, when using discovery, both candidates. Prepare each distinct source per generation. Plan and render the selected assets with Favigen’s staged API. Hold a complete generation as an immutable snapshot. Keep its render recipes and cached bytes independent of deployment base, names, manifest metadata, and output directory. A warm process can reuse prepared sources when unchanged and a warm disk hit reuses pixel bytes after source validation. Cache read/write failures warn once per distinct problem and act as misses. [Favigen staged API](https://github.com/josh-hemphill/favigen/tree/v1.2.0#render-and-publish-independently)

**Dev.** Register middleware before Vite’s base middleware. Match the request pathname against an allowlist of complete published paths prefixed with the effective dev base. Vite uses only the pathname part of a full URL base in dev. Leave unrelated paths to Vite. HTML post-transforms, companion API calls, and direct first GET/HEAD requests to a configured stable ICO, basic manifest or fragment share one lazy render attempt. Serve GET and HEAD with the correct type, length and ETag, including conditional 304s. Keep the current and previous completed digest URLs through a reload. Stable routes revalidate. During initial invalid or absent artwork, serve the app with authored markup, omit generated links, and return 404 on the unavailable managed routes. Report the source and target, with the fix where known. After a broken edit retain the last complete generation. Watch changes, add/unlink and atomic saves, including missing candidates via their nearest existing parent. Debounce saves, ignore superseded results, and send one full reload when the latest successful generation changes the publication. Release watcher listeners and pending reloads on shutdown. [Vite dev server and HTML hooks](https://vite.dev/guide/api-plugin)

**Dev route ownership.** Public files take precedence at matching managed paths, including files added while dev is running. Check route availability during publication, before responding or generating links, and on public-file add/unlink so assets, HTML and the companion API follow the same decision. When a collision occurs, defer the request to Vite, omit that generated icon from the effective dev publication, and warn once per path. Derive both HTML and the companion API from that publication. Reload when ownership changes. For example, a public `favicon.ico` suppresses the requested root ICO alias and keeps the namespaced PNGs. A public basic manifest suppresses the generated manifest route and link, preserving any authored link. Also withhold the built-in route and link if public files make either required regular app icon unavailable. A public fragment takes over its exact route. If an HTML page already has a manifest link, omit the built-in link for that page and report the conflict. Unlinking the public file restores the managed route after reevaluation.

**Build and watch.** Restrict build emission to the client application. Use Vite’s normal HTML entries for auto-injection. Library and SSR builds skip generation. A client backend build with a JS entry can still emit assets and use the API or fragment below. In `buildStart`, register watched sources before preparation and invalidate the previous active generation. A failed render aborts the build before output preparation. A late error may occur after Vite has cleaned `dist`. Deploy only after a successful build and build in a staging directory if the previous deployment tree must survive every failure. Watch must recover on recreation and generate current URLs, including after a failed build or cache hit. Watch parents for missing paths where required by the bundler. Use fresh emission references per output. Preview serves the successful built tree. A clean build contains the current set. With an uncleared output directory, Vite’s cleanup policy governs obsolete files.

**Output hook order.** Return a Vite plugin array containing the normal-order `vite-plugin-favicon` producer and its internal validator. Expose the public API on the producer. Put companion consumers and output writers after the producer in resolved order and before the `enforce: 'post'` validator. All three use `generateBundle` with `order: 'post'`. Vite’s HTML is available to the producer. It validates candidate paths before emitting explicit filenames, uses the current output’s `getFileName`, binds URLs per referrer, then parses and splices its links into the HTML. This preserves unrelated markup. Companions can then inspect the emitted assets from their own hook. The validator inspects its current bundle view, checks the finalized bytes and references, and rejects the output before a successful result even with `write: false`. A supported integration completes its writes before this validator. A plugin ordered after the validator or rewriting files during or after disk publication owns its changes. Document the resolved ordering and test an output writer in the supported window.

**Collision checks.** Compare generated paths case-insensitively for portable output. Reject absolute output names, parent traversal, unsafe URL path segments and generated duplicate paths. Before emission, check emitted names and inspect the resolved public directory separately when Vite is configured to copy it. Treat an occupied path as an error even when the current configuration requests in-memory output. In the validator, check each claimed filename, bytes or digest and plugin-owned links, and enforce single-link ownership for a basic manifest. Promote a Rollup `FILE_NAME_CONFLICT` log for a path claimed by this plugin to a build error, including when Rollup keeps the original bytes. The tested Rollup log exposes the filename in its message. Pin the tested message handling in the fixture and leave other warnings to the app’s usual logging hooks. Verify that a late conflict fails before a successful build result with a duplicate emitter and a direct mutation in both bundlers. Permit one favicon plugin instance per Vite project. [Vite plugin ordering](https://vite.dev/guide/api-plugin#plugin-ordering) · [Rollup logging hook](https://rollupjs.org/plugin-development/#onlog)

**URL calculation.** Build references use the actual emitted filename and the relevant referencing document. Use the same URL resolution for HTML and the API and encode path segments once. Under `/` or a base such as `/shop/`, each HTML page gets a root-relative URL under that base. Under `./` or an empty base, calculate per document from its emitted directory using POSIX paths. A full URL base puts production icon URLs on that origin, with a companion or the built-in helper controlling any same-origin manifest link. HTML with an authored `<base href>` that changes generated URL resolution gets a diagnostic with the option to manage links explicitly via `inject: false`. Projects that set Vite’s experimental `renderBuiltUrl` must use a documented, synchronous `resolveIconUrl({ outputFileName, referrerFile, defaultUrl })` override for icon references in build, or remove the experimental setting in that build. Verify the override returns a static HTTP(S), root-relative, or document-relative URL. [Vite base options](https://vite.dev/config/shared-options.html#base) · [Vite relative base](https://vite.dev/guide/build.html#relative-base) · [Vite advanced base options](https://vite.dev/guide/build.html#advanced-base-options)

| Production context | Browser page references generated icon at | Companion manifest icon reference |
| --- | --- | --- |
| `base: '/shop/'`, page `help/index.html` | `/shop/assets/favicons/icon.<digest>.png` | `/shop/assets/favicons/icon.<digest>.png` |
| `base: './'`, page `help/topics/index.html`, manifest `meta/app.webmanifest` | `../../assets/favicons/icon.<digest>.png` | `../assets/favicons/icon.<digest>.png` |
| `base: 'https://cdn.example/brand/'` | `https://cdn.example/brand/assets/favicons/icon.<digest>.png` | Same absolute URL, with the app-origin manifest served separately |

The table shows path shapes. Browser links refer to favicon or touch assets. A companion manifest references a separate app-role asset from the same generation.

## Manifest and backend integrations

Keep the manifest off by default, including with `profile: 'pwa'`. The basic helper writes `manifest.webmanifest` relative to the app root and adds one link when injection is enabled. It accepts a name, optional short name, colors, display mode, `startUrl` and `scope`. Launch and scope default to the app root. For a relative base, use `./` from the root manifest. For a subpath base, use `/shop/` for both. Resolve explicit launch and scope relative to the manifest and validate origin and containment. The helper supplies a web app manifest and icon metadata. Service workers and offline behavior belong to the host application. [Favigen manifest helper](https://github.com/josh-hemphill/favigen/blob/v1.2.0/src/publication.ts) · [Web App Manifest](https://www.w3.org/TR/appmanifest/)

For a full CDN base such as `https://cdn.example/brand/`, require a production `manifest.appBase` such as `https://app.example/shop/`. Serve the built manifest at the app base and its icons at the CDN base. Validate off-origin icons with the actual deployment’s response headers and browser. In dev, Vite serves the app and manifest at the local pathname mount `/brand/`. Resolve an explicit production launch or scope against the production manifest URL before remapping. Check its origin and that its normalized path starts at the production directory boundary `/shop/`. Replace that directory prefix with `/brand/`, preserve the launch query and fragment, and validate the mapped launch against the mapped scope. This works for relative, root-relative, and absolute option values that resolve within the production app mount. Reject values outside that mount, including a sibling such as `/shop-other/`. The diagnostic names the option and suggests an app-relative value or a companion for a broader scope.

For example, an explicit production launch at `https://app.example/shop/custom?source=launcher#top` and scope `https://app.example/shop/` map to `/brand/custom?source=launcher#top` and `/brand/` in dev. The icon paths also use `/brand/` locally. A scratch fixture confirmed that this mapped launch reached the app on Vite 7 and 8 and that the unmapped `/shop/custom` returned 404. [Vite full URL base in dev](https://vite.dev/config/shared-options.html#base)

A companion may declare `plugin.api.favigenManifest = { version: 1, owner: 'plugin-name' }`. During resolved configuration, reject two declared owners or a declared owner plus basic mode. An existing undeclared PWA plugin works with our manifest mode off. In basic mode, an existing manifest link, public file at the fallback path, or output conflict surfaces an error pointing to the owner and how to disable basic mode. Use the public-file and authored-link precedence rules above during dev. With `inject: false`, skip HTML checks and emit only the explicitly requested files. A companion that emits its own manifest must run with basic mode disabled. The late validator checks for a single manifest link when basic injection is enabled.

Expose a documented Vite plugin API backed by Favigen’s `IconPublication` envelope and re-export the types from the plugin. Consumers receive immutable records with stable IDs, roles, MIME types, sizes, optional purpose, output filenames, URLs, and byte digests.

```ts
interface ViteFavigenApi {
  readonly version: 1
  getDevIcons(): Promise<IconPublication | undefined>
  resolveBuildIcons(context: {
    readAsset: (fileName: string) => string | Uint8Array | undefined
    referrerFile: string
  }): IconPublication
}
```

- A companion finds `plugin.api.favigen` in `configResolved` and checks the API version. In dev, its async HTML and manifest middleware call `getDevIcons()`. It awaits the first completed attempt, yields undefined on initial failure, and returns the last complete snapshot during or after a failed edit. The companion gates its file and link on readiness and checks for any app icon IDs it requires. In dev `outputFileName` is the app-relative route path before the Vite base is prefixed. `url` is the effective root-relative dev request path. These describe an in-memory asset.
- Call `resolveBuildIcons` during the companion’s post-ordered `generateBundle` after the producer and before validation. Pass a lookup into the current output and the output-relative referring filename. This callback avoids exposing a Rollup- or Rolldown-specific bundle type. The adapter checks that its current generation has been emitted and that the expected filenames and bytes are visible to the caller. An early call, missing asset, or different bytes produces a diagnostic naming the required hook and order. Passing the current hook’s view is part of the contract. Identical bytes in another output have the same binding, and byte validation cannot distinguish two such outputs. Bind the companion manifest relative to its own emitted path and link to it separately from each HTML page.
- For Laravel, Rails or custom HTML, `inject: false` leaves assets and API available for a backend template plugin. Offer explicit `htmlFragment: { file: 'meta/favicon-links.html', referrerFile: 'index.html' }` for a string include. Resolve references against the intended served document mapped into the output tree, including launch and manifest links when basic mode is enabled. In relative-base deployments, configure the fragment for the consuming document depth. Use a pathname base for one include shared across different route depths. Serve the fragment with equivalent dev-base URLs and revalidation when requested from the configured path. Emit the fragment only when requested and apply the same path and ownership checks as for the manifest. If backend HTML runs on a separate dev origin, proxy the managed icon and manifest routes to Vite to use the fragment’s root-relative links. An integration that owns its HTML can use the API and resolve icon URLs against the Vite dev origin instead, while keeping any web app manifest at the app origin. [Vite backend integration](https://vite.dev/guide/backend-integration.html)

For example, configure `plugins: [favicons({ source: './src/brand.svg', profile: 'pwa' }), companion]`. The companion reads the versioned API in `configResolved`. Its output hook can then emit the manifest using the generated app icons. The example shows file emission. The companion also publishes its link using the referring page’s base and directory.

```ts
// Within the companion’s post-ordered generateBundle handler.
const manifestFile = 'meta/app.webmanifest'
const publication = iconApi.resolveBuildIcons({
  referrerFile: manifestFile,
  readAsset(fileName) {
    const entry = bundle[fileName]
    return entry?.type === 'asset' ? entry.source : undefined
  },
})
const icons = publication.icons.filter(icon => icon.role === 'app').map(icon => ({
  src: icon.url,
  sizes: icon.sizes.map(({ width, height }) => `${width}x${height}`).join(' '),
  type: icon.mimeType,
  purpose: icon.purpose ?? 'any',
}))
this.emitFile({
  type: 'asset',
  fileName: manifestFile,
  source: JSON.stringify({ name: 'Shop', start_url: '../', scope: '../', icons }),
})
```

With `base: './'`, `help/topics/index.html` links to `../../meta/app.webmanifest`. The manifest’s `app.any.192` record uses `../assets/favicons/icon-192.<digest>.png`, which resolves to a 192 × 192 PNG whose digest matches the publication. The example’s `start_url` and `scope` launch the app at the deployment root relative to that nested manifest.

## Upgrading from 1.0.8

| Existing usage | 2.x outcome and upgrade step |
| --- | --- |
| Default/named ESM export, CJS `require`, positional logo, `logo`, `inject` | Retain the existing ESM and CJS aliases. Bare `require('vite-plugin-favicon')` becomes callable, with `.default` and `.ViteFaviconsPlugin` aliases. Use `source` in new configs. Conflicting `source` and `logo` values get a migration error. `assets/logo.png` still works with implicit discovery. |
| Relative logo or `projectRoot` | Source resolution follows Vite’s root. Supply an absolute source if it previously relied on the process working directory. A removed `projectRoot` option gets a diagnostic. Set Vite’s `root` only when moving the whole project. To replace metadata inference, assign `manifest.name` or configure the manifest owner. |
| `favicons` config including `appName`, platform lists, and icon tuning | An actionable config error names the provided keys. Move `appName` to a basic manifest’s `name` or to your manifest owner. Move output selection to `profile` and `ids`, and image settings to `render`, `variants` or `targets`. Use checked-in public assets or a separate generator for startup screens and vendor-specific targets outside the two profiles. Document the supported IDs in the migration guide. |
| Former `outputPath`, `publicPath`, `prefix`, `cache` | Move emitted locations to `outputDir` and serving prefixes to Vite’s `base`. Use `resolveIconUrl` for advanced static deployment mappings. `cache: false` now disables caching. A legacy `cache: true` selects the default directory. Errors for removed keys point to their replacements. |
| Legacy auto-generated manifest, fixed paths, and starter assets | Opt in via `manifest: { mode: 'basic', name: '…' }` or use `profile: 'pwa'` with a manifest owner. Update hardcoded paths through the generated links or API. Existing authored links and public assets are retained. Remove the old icon link from a starter template to switch over, and remove the old public ICO only if taking over the root fallback. |
| Vite 2–6 or Node below the new floor | Use the 1.x line while migrating the app. The peer range also excludes earlier Vite 7 and 8 minors, which can upgrade within their major. Choose a tested Vite/Node combination before upgrading the plugin. Record the historical 1.x issues in the migration docs. |
